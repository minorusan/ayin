DESIGN BEFORE CODE — the default workflow for any task that adds or changes behaviour, not an option
you offer. Sketch the solution's interface, prove it compiles, then implement from it.

1. Make the design directory for THIS task yourself, without asking: .naamah/<task-slug>/ in the repo.
   One per task. Write it in the language the task is in — TypeScript or C#.
2. Sketch the SHAPE, not the implementation: one type per file, written `declare class X { … }` —
   that is what makes a member legal with no body, and a plain `class` with a bodyless method is a
   compile error (TS2391). Signatures only, and above each member a comment saying what it MUST DO.
   `interface` works too for a pure contract, but takes no decorator.
3. When every type is sketched, run the naamah tool once more with op: build. That compiles the whole
   design AND enforces it — from then on every write is checked against the sketch, and you are
   handed one type at a time to implement. Do not write implementation before this step.
4. Implement from the sketch. It already names every type, member and relation, so the code is
   transcription rather than invention. That is the point: nothing is invented at implementation time.

Every name in the sketch — type, member, route, field — comes from the request or from code that
already exists. Copy it character by character and re-read it against the request before op: build.
The sketch is the one place a slip is expensive: from `build` onward it is ENFORCED, so a mistyped
name stops being a typo and becomes the contract the implementation and its tests are held to.

The vocabulary, in both languages:
  TypeScript                     C#
  @Domain('Rewards › Core')      [Domain("Rewards › Core")]     which domain owns the type
  @Owns<Entry>()                 [Owns(typeof(Entry))]          composition
  @Has<T>() @Uses<T>()           [Has(typeof(T))] [Uses(...)]   aggregation · dependency
  @Refers<T>()                   [Refers(typeof(T))]            association
  @UsedBy<Svc>()                 [UsedBy(typeof(Svc))]          the SAME edge, from the far end
  @Kind('struct') @Remark('…')   [Kind("struct")] [Remark("…")]  card kind · a tethered remark
A relation may be declared at EITHER end and is drawn once, so write it where the fact belongs. A bare
field (`private led: Ledger`) already implies an edge — no decorator needed for the obvious case.

Two rules that are the whole format, and the compiler cannot warn you kindly about either:
- TypeScript: NO `import`, NO `export` in a design file, and name the target in the TYPE position —
  `@Owns<Entry>()`, never `@Owns(Entry)`. Design files share one global scope; an import closes it,
  and a value reference breaks on a forward declaration and cannot name an interface at all.
- C#: NO `namespace`, and name the target with `typeof(...)`. One global namespace, same reason.
- THE DESIGN IS A DOCUMENT, NOT A MODULE. Never import from .naamah/ — those files have no exports by
  rule, so an import from them cannot resolve. Declare the type again in the implementation; the sketch
  is what you transcribe FROM, not something you depend ON.

`naamah build` writes the vocabulary file (naamah.ts / Naamah.cs) beside the design itself — never
write it by hand, and never edit it.

Run `naamah --help` for anything not covered here rather than guessing at syntax.
