Decide what KIND of request this is, and whether it needs a written plan.

FIRST, `kind` — what the person gets at the end:
  build        the repository ends up different. Code, config or assets are written, changed or deleted.
  investigate  a QUESTION about this codebase, answered by reading it. Nothing is written. "Does X
               happen anywhere", "trace where Y comes from", "is this value baked in or set at
               runtime", "which files would Z touch".
  answer       a question that reading this codebase cannot settle: an opinion, a preference, a
               discussion about the tools or the assistant itself, small talk, a design argument.

`kind` is decided on WHAT THE PERSON ENDS UP WITH, never on the work it implies along the way. "Add
logging to the score flow" is build. "Where does the score come from" is investigate, even if the
answer would take an hour. "What do you think of your own tools" is answer, even when it mentions
files.

A request that says LOOK AROUND AND THEN TELL ME WHAT YOU THINK is `answer`. Being asked to open
files, try a tool or poke at the project does not make it investigate: the deliverable is the
opinion, and no fact in the repository settles it. Investigate is for a question the code has a
right answer to.

THEN `complex` — whether the work spans several features or subsystems, mixes UI with backend, adds a
new surface (a webview, a service, a data store), or holds several independently-shippable asks. One
change described at length is not complex: a detailed bug report, a long explanation of one feature, a
paste of logs with one question.

REQUEST:
{{REQUEST}}

Also list every THIRD-PARTY API or external service the work would have to talk to — anything not
running on the user's own machine: a vendor REST API, a SaaS product, an OAuth provider, a payment or
messaging or maps or model provider. Name the service, not the library ("Stripe", not "stripe-node").
List them even when the request only implies them, and leave the list empty when the work is purely
local. This list is mandatory input to a fresh documentation lookup, so a missed API means the plan
gets written from stale memory.

If the request names a NEW FOLDER to create the project in — "a website in testwebsite-2", "set up
foo-service" — give that folder's name in `projectDir`: one path segment, no slashes, exactly as
written. Empty when the request names no folder, and empty when it only names a language, a framework
or the thing being built.

Respond with exactly one JSON object and nothing else:
